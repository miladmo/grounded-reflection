# Synthetic work decisions v0.2

These materials are authored fixtures, not observations or model results. All organisations, reviewers, documents, activities and tool responses are fictional. There is no industry-partner, employee, customer or proprietary data.

## Contents and generation

`grounded_reflection.pilot_v02.data.generate_histories(seed)` produces eight work episodes for each of recruiting, sales and research. Four episodes combine situated corrections with accepted decisions across two audiences. Two show accepted decisions in another workflow, one for each audience. One combines a locally commissioned change for a showcase with contrasting closing drafts from two editors in the same review batch. The final episode records a save failure and a successful retry.

`generate_tasks(split, seed)` produces only the requested split. Calibration round 2 has one transfer case with withheld workflow knowledge and one boundary case with complete current instructions per family. These are three transfer cases and three instruction-following anchors. Validation has one boundary case and one missing-audience case per family. The final layout has transfer, boundary, current override and missing-audience cases per family. Concrete final cases must only be generated after freeze with the separate final seed. Development generation and data-only tests do not request final cases. Integration tests generate disposable offline mock final cases after their own test freeze. Those test fixtures are not an empirical final evaluation set.

The first calibration round used two transfer cases per family and observed low compliance by the no-history baseline, which sometimes asked for the unavailable workflow information. Round 2 replaces only the second calibration case in each family with an explicit anchor. It retains six cases and two repetitions. Histories, world rules, validation cases and the final-case generator are unchanged. Reaching the approximately 30–70 percent calibration band with this mixed composition would not establish moderate difficulty on the hidden requirements. Report anchors and transfer cases separately. Asking for genuinely unavailable knowledge can be a legitimate response by the no-history baseline even when the task-completion score is low.

`write_development(data_directory, seed=20260928)` writes the histories, calibration and validation cases and their separate evaluator records. It refuses to replace existing files. For example, pass `Path('pilots/v02/data')` from the repository root. The supplied development material uses seed `20260928`.

Seeded case facts, document identifiers and subject names change between splits and seeds. The requirements of the fictional world deliberately do not change with the seed. Changing a final seed therefore creates new instances of the same learnable requirements rather than introducing a different policy. `task_content_fingerprint` excludes case ID and split when checking copied cases, so merely relabelling a task does not evade duplicate detection.

## Information boundaries

Public task inputs contain context, factual source material, the current request and common field names. Current override or boundary requirements are explicit when appropriate. Ordinary transfer tasks omit the correct emphasis and route. Accepted historical outputs expose the values actually used. Feedback explains professional concerns in natural language, such as missing ownership information or uncertainty about the customer's needs. It does not state reusable field assignments or identify which observations should become requirements.

`ground_truth/families.json` contains recoverable rules, supported local exceptions, unresolved alternatives, misleading generalisations and scope probes. `ground_truth/calibration.json` and `ground_truth/validation.json` contain case-specific checks and action decisions. These files belong exclusively to evaluation and must never enter preparation or generation payloads. Family rule generation is separate from history generation.

Each family supports two audience-specific default emphases and a channel-specific route, subject to current instructions. Repeated accepted decisions provide positive evidence. Accepted decisions with different values in the other audience and channel provide concrete counterexamples to broader emphasis rules. The route is observed for both audiences, so restricting it to one audience would discard supported coverage. Both other-channel cases use a different route. Scope is assessed over these observed distinctions, not by treating every unobserved context as a counterexample or claiming a uniquely identifiable policy outside them.

The showcase opening is changed and accepted for that specific commission. Other accepted records support a different default, so this local change does not establish a standing requirement for the whole workflow. It is not labelled as a personal or rejected preference in model inputs. Closing drafts reflect contrasting suggestions by equally titled editors in the same batch; the export contains no release receipt. Neither closing choice is established as a standing requirement. The tool evidence consists of a 503 response offering another route and a 200 response from the original destination. It contains no instruction telling the model which future route to adopt.

The public context includes `occasion=routine` on ordinary records and tasks, and `occasion=showcase` on the commissioned presentation. This observed distinction allows a local scope to be expressed without adding an evaluator label. The evaluator recognises the other workflow's emphasis and route within that workflow, and the showcase emphasis within its observed channel, audience and occasion. These `supported_exceptions` are valid local findings rather than false positives or primary recall targets. Their adoption is reported separately. A rule qualifies only when both its predicate/value and its declared scope match a supported exception or a narrower scope. Adopting the same value broadly across the ordinary workflow remains unsupported.

## Decisions and measurement

Tasks request `emphasis`, `route`, `source_id` and a factual `summary`. These are small structured decisions, not full recruiting campaigns, sales performance or scientific output. A source ID and subject-name inclusion check are deliberately simple controls. Hidden requirement compliance is reported separately so those controls cannot mask unsuccessful adaptation.

An absent audience makes the appropriate emphasis unidentifiable. The common output convention uses `undetermined` or omits unresolved fields and asks for the missing audience or defers. Independently supported fields may be retained, but their omission during valid clarification is not a failure to deliver. The oracle does not demand guessing an arbitrary preference. The `unresolved_output_fields` record prevents a guessed emphasis from passing merely because the model also asks a question. A current record-specific override takes precedence over historical practice. Asking on adequately specified tasks is unnecessary abstention.

## Limitations

The values and contexts are deliberately narrow. Some meaning must be reconstructed from situated corrections, accepted changes and context, while accepted structured records still state observable decisions explicitly. This is a minimal synthetic test of evidence synthesis, scope and downstream use. It is not a natural enterprise dataset or a demonstration of discovering tacit organisational knowledge in raw production logs. The tasks share an authored template and three fictional contexts. New identifiers and facts do not make them independent organisations or demonstrate broader transfer.

Deterministic scores assess the stated decisions and surface checks, not the semantic completeness or professional usefulness of prose. No tool is actually called. No live model calibration, practitioner review or repeated adaptation has occurred merely because these files exist. The mock backend cannot establish the intended calibration band or any advantage of reflection.
