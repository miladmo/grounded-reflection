Shared public rule and output contract, version 2. The same contract applies to every preparation and generation procedure.

The initial configuration is already in force. At generation time, task.baseline_fields contains its fully constructed output, including any configured formatting. A rule is an executable transformation of that baseline, not a description of a desired final state. Evidence confirming the existing baseline needs no additional change rule; record that confirmation in notes when useful. Do not turn "retain the configured behavior" into an extra transformation.

Rules contain field, operation, value, separator and scope. Let baseline be the field-name-to-value mapping in task.baseline_fields, and facts be task.facts. All applicable rules read the same immutable baseline; they do not run sequentially on each other's output. The operations mean exactly:
- omit: remove field; value and separator are empty.
- set_literal: assign value to field exactly; separator is empty.
- set_fact: assign facts[value] to field; separator is empty.
- append_fact: assign baseline[field] + separator + facts[value] to field. The baseline field must exist. This operation appends once to the complete baseline value. It does not deduplicate, ensure that a suffix is present, remove existing text, or reconstruct a value from a different fact.
Fact operations name available fact keys, not invented future values. Preserve fields that no applicable rule changes. Conflicting assignments to the same field are invalid rather than resolved by rule order. Use exact public field names and the representations specified by field_dictionary; do not invent equivalent-looking value encodings or conversions.

Scope is a conjunction: every named context attribute must match one of its listed values. A missing attribute makes applicability unknown, not true. Encode Scope.match as [{"attribute":"context_key","values":["allowed_value"]}]. Keep work role, reviewer, task family and workflow distinct. Use the supplied assumptions and history to justify scope.

When a preparation stage assigns epistemic candidate status, adopt means the evidence warrants that operational rule at that scope; reject means the evidence contradicts the rule; unresolved means the available evidence does not settle it. Not authorising an update now is not itself a rejection. An inadequate justification does not establish that the proposed rule is false. Preserve genuine uncertainty and supported partial rules. In a ReflectionDraft, status=unresolved instead marks an uncommitted provisional candidate awaiting the planned audit; it is not an epistemic verdict. Only final adopted rules become instructions. Rejected and unresolved candidates never become runtime instructions or blocking questions.

For WorkOutput, decision describes the net field change from task.baseline_fields. Use apply if at least one field value or field presence changes; use keep if the final fields equal the baseline. Faithfully apply supplied adopted instructions and report the rules actually applied. An applicable rule can leave the fields unchanged; such no-op applied_rules are allowed with decision=keep. Do not add a change merely to justify an apply label, and do not silently repair or reinterpret a supplied rule. Each output field is {"name":"exact_field_name","value":"text"}. Include every schema property. Employee questions are outside this experiment; questions must be [], and completed reflects actual delivery of the requested synthetic output.
